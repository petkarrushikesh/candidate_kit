# Review of the starter application

The findings below refer to the original starter `app/main.py`. I compared its behavior with the API contract and then applied the fixes in `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | It builds the shift start by replacing the punch-in's clock fields. This does not account for IST conversion or an overnight shift that began the previous day. | Give it a UTC punch timestamp near midnight or a 04:00 IST punch for a 22:00–06:00 shift; its late result/date can be wrong. | Convert instants to IST, determine the attendance shift date (including overnight shifts), truncate to seconds, then calculate lateness against the correct shift start. |
| 2 | `compute_work_hours` | Python `round()` uses ties-to-even, but the contract requires half-up rounding to two decimal places. | Use a duration whose hour value is exactly halfway between two hundredths; the result can differ from the contract. | Use `Decimal` with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | It always places `shift_end` on `date_str` and counts every positive minute. It therefore mishandles overnight shifts and fails to enforce the 30-minute minimum. | For a 22:00–06:00 shift, punch out at 06:20 the next day; the starter can calculate against the wrong day's 06:00 and report overtime below the required threshold. | Resolve the shift end from the attendance date and overnight rule; count whole minutes only when the difference is at least 30 minutes. |
| 4 | `/health` | It always reports healthy without checking MongoDB. | Stop MongoDB and call `/health`; the starter still returns 200. | Ping MongoDB and return 503 if the ping fails. |
| 5 | `create_employee` | A check-then-insert duplicate check is race-prone, and the starter has no unique `emp_code` index. It also stores a naive `created_at` and does not reject equal shift start/end values. | Send simultaneous creates for one code, or submit equal shift times. The starter can insert duplicates or accept invalid shifts. | Add a unique index and map duplicate-key errors to 409; validate distinct shift times and store UTC creation time. |
| 6 | `list_employees` | `skip` is `page * page_size`, the total ignores the department filter, and results are not sorted by `emp_code`. | Page 1 starts after the first page of records; filtered total disagrees with the result set. | Use `(page - 1) * page_size`, count using the same filter, sort ascending, and enforce pagination limits. |
| 7 | `punch_in` | It dereferences an unknown employee, uses the machine's local timezone for the timestamp/date, checks for duplicates before inserting, accepts invalid statuses, and returns an internal Mongo ID as `id`. | Try an unknown code, a UTC timestamp whose IST date differs, concurrent punches, an invalid status, or inspect the response. | Return 404 for unknown employees; use validated epoch milliseconds and IST shift-date logic; rely on the unique `(emp_code, date)` index for race-safe 409 behavior; return the contract fields without Mongo IDs. |
| 8 | `list_attendance` | It loads every matching record into Python before sorting and paging, sorts only by date, and includes Mongo IDs in the response. It also lacks proper date and pagination validation. | Use a large collection, tied dates, invalid date ranges, or inspect record fields; the query is inefficient and the response/validation differs from the contract. | Count filtered records and perform sorting, skip, and limit in MongoDB; sort by date descending then code ascending; validate inputs and omit internal IDs. |
| 9 | Missing routes | The starter does not implement punch-out, regularization, any of the four analytics routes, or the explain route. | Request any of these documented paths; the starter returns 404. | Implemented the routes and their contract-specific validation, aggregation, history, and response behavior in `app/main.py`. |
| 10 | Added `/admin/explain/{endpoint}` response | MongoDB explain documents may contain BSON values such as `Timestamp` that FastAPI's default encoder cannot serialize. | Call a valid explain endpoint and observe a serialization error when BSON-only values are present. | Convert the explain result through `bson.json_util.dumps()` and `json.loads()` before returning it. |

## Gemini suggestions checked

- **`fail422` positional arguments:** Not a defect. `HTTPException(422, message)` passes `status_code` and `detail` positionally; named arguments are clearer but do not prevent a 500.
- **Explain `limit: 0`:** Not a defect by itself. MongoDB documents `limit: 0` as unbounded behavior. The current helper omits zero/unspecified skip and limit values anyway. See the [MongoDB find command reference](https://www.mongodb.com/docs/manual/reference/command/find/).
- **Explain BSON serialization:** A real issue in the added explain implementation; fixed with `json_util` conversion above.
- **Trend rounding nulls:** Not a defect in the reviewed version: it already checked each value for `None` before rounding. Null is expected for weekends or days with no headcount. The current code retains those checks.
